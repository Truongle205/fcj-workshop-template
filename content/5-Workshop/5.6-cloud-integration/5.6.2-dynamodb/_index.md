# Overview

Amazon DynamoDB is a fully managed NoSQL database service designed for applications that require low latency and high scalability.

Instead of managing database servers, users only define the table schema and primary key. AWS automatically handles storage, scaling, replication, and availability.

In this project, DynamoDB stores every telemetry message published by the ESP32-S3.

# Why DynamoDB?

Telemetry data is generated continuously.

A relational database would require connection management and schema maintenance.

Amazon DynamoDB is well suited because it provides:

- Fully managed service.
- Automatic scaling.
- Low latency.
- High availability.
- Native integration with AWS IoT Rules Engine.

No application server is required.

# Step 1 – Open Amazon DynamoDB

Open the AWS Management Console.

Navigate to:

```text
Amazon DynamoDB
→ Tables
```

Choose:

```text
Create table
```

---

# Step 2 – Create the Table

Configure the table as follows.

| Setting | Value |
|----------|-------|
| Table name | SmartHomeTelemetry |
| Partition key | device_id (String) |
| Sort key | timestamp (Number) |

Choose:

```text
On-demand
```

for Capacity Mode.

{{% notice note %}}
On-demand capacity automatically adjusts throughput based on incoming traffic and is appropriate for workshop and development environments.
{{% /notice %}}

---

# Why Use Two Keys?

The primary key consists of:

```text
device_id
timestamp
```

Example:

```text
device_id = esp32-home-01

timestamp = 1784900000
```

Advantages:

- Stores multiple telemetry records for the same device.
- Allows efficient time-based queries.
- Prevents duplicate primary keys.

---

# Step 3 – Configure the IoT Rule Action

Return to:

```text
AWS IoT Core
→ Message routing
→ Rules
```

Open:

```text
StoreSmartHomeTelemetry
```

Configure the DynamoDB action.

Select:

```text
SmartHomeTelemetry
```

as the destination table.

Map the payload fields to DynamoDB attributes.

Typical attributes:

| Attribute | Type |
|-----------|------|
| device_id | String |
| timestamp | Number |
| temperature | Number |
| humidity | Number |
| light | Number |
| door_open | Boolean |
| relay_on | Boolean |

The IAM role configured earlier grants permission to perform:

```text
dynamodb:PutItem
```

---

# Step 4 – Publish Telemetry

Run the ESP32-S3 firmware.

The device periodically publishes telemetry every:

```text
10 seconds
```

Example payload:

```json
{
  "device_id":"esp32-home-01",
  "timestamp":1784900000,
  "temperature":29.4,
  "humidity":71,
  "light":870,
  "door_open":false,
  "relay_on":false
}
```

AWS IoT Rule receives this message and inserts a new item into DynamoDB.

---

# Step 5 – Verify the Data

Open:

```text
Amazon DynamoDB
→ Tables
→ SmartHomeTelemetry
→ Explore table items
```

You should see records similar to:

| device_id | timestamp | temperature |

| esp32-home-01 | 1784900000 | 29.4 |

# Understanding the Data Flow

The storage workflow is:

```text
ESP32-S3
      ↓
Telemetry JSON
      ↓
AWS IoT Core
      ↓
AWS IoT Rule
      ↓
Amazon DynamoDB
```

The ESP32-S3 does not communicate with DynamoDB directly.

Only AWS IoT Rules Engine writes data into the table.

# Troubleshooting

## No records appear

Verify:

- ESP32-S3 is publishing telemetry.
- The MQTT topic matches the SQL statement.
- The IoT Rule is enabled.
- The IAM role has `dynamodb:PutItem`.
- The DynamoDB table exists.

---

## Missing attributes

Verify:

- The telemetry JSON contains the expected fields.
- The IoT Rule action maps the payload correctly.

---

## Duplicate primary key

If two records have the same:

```text
device_id
timestamp
```

the second write replaces the first.

Use Unix timestamps with second precision or higher to reduce the chance of collisions.
